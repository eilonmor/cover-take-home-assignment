## 2. מבנה השכבות

הקוד מחולק לשכבות. כל שכבה תלויה רק בשכבות שמתחתיה:

```
specs/*.md                       אפיון: User Stories, ACs, חוזה UI, באגים ידועים
   │
tests/<area>/*.spec.ts           הטסטים: תרחיש + assertions עסקיים בלבד
   │  import { test, expect } from '@fixtures/index'
   ▼
src/fixtures/                    נקודת כניסה אחת: auth + page objects + Allure + custom matchers
   │
src/pages/                       Page Object Model
   ├── BasePage / AppPage        בסיס משותף (goto, waitForLoaded, header, menu, title)
   ├── components/               Header, BurgerMenu, ItemList
   ├── flows/ShopFlow            מסעות רב-עמודיים (עגלה → checkout → הזמנה)
   └── *Page.ts                  מחלקה לכל עמוד
   │
src/data/  src/utils/            נתונים מוקלדים (מוצרים, הודעות, נתיבים, משתמשים)
                                 ועזרים (כסף בסנטים, grouped runner, storage, env, timeouts)

playwright.config.ts · src/global-setup.ts · src/reporters/ · .github/workflows/
```

**כלל הזהב:** selectors קיימים רק תחת `src/pages/**`, טקסטים ונתונים רק תחת `src/data/**`, וה-assertions העסקיים רק בקבצי ה-spec.

## 3. החלטות תכנון

לכל החלטה: מה הוחלט, למה, יתרונות וחסרונות.

### 3.1 קודם אפיון, אחר כך טסטים (Specs-first) עם Playwright Test Agents

**ההחלטה:** לפני שנכתב טסט אחד, ה-planner agent של Playwright סייר באתר החי וכתב לכל אזור מסמך אפיון בסגנון PM, עם User Stories, Acceptance Criteria בפורמט Given/When/Then, חוזה UI (מזהי `data-test`), מקרי קצה ובאגים שנצפו. מכל אפיון נבחרו 6 תרחישים (Selected) והשאר נשארו ב-Backlog. ה-generator יצר טיוטה לכל טסט, והיא נכתבה מחדש על גבי ה-fixtures וה-page objects של הפרויקט. ה-healer שימש לדיבוג טיוטות שנכשלו.

**למה:** המשימה מבקשת "לבחור בעצמך את מקרי הבדיקה". אפיון כתוב מאפשר לבחור לפי עדיפות וכיסוי ולא לפי מה שקל לאוטומט, ונותן מקור אמת אחד להתנהגות הצפויה.

| יתרונות | חסרונות |
|---------|---------|
| עקיבות מלאה: TC → AC → User Story (דרך שם הטסט וה-annotation `covers`) | השקעה מוקדמת לפני שרואים טסט רץ |
| הבחירה של 6 טסטים לאזור מנומקת ומתועדת, וה-Backlog מסביר מה נשאר בחוץ ולמה | האפיון נכתב מתוך צפייה באתר, כך שיש לשפוט מה "מכוון" ומה באג |
| באגים התגלו כבר בשלב האפיון ולא הפכו בטעות לקריטריון קבלה | הטיוטות של ה-generator דרשו שכתוב כדי להתאים לקונבנציות |

### 3.2 הטסטים בודקים את ההתנהגות המכוונת, ובאגים ידועים מתועדים ולא נבדקים

**ההחלטה:** טסט לעולם לא מאשר באג כהתנהגות נכונה. כשבאג ידוע מופיע בתוך טסט נבחר, הוא נרשם כ-annotation מסוג `known-issue`, ורק כל עוד הבאג אכן מופיע. תרחישים שכל מטרתם היא באג ידוע (למשל checkout עם עגלה ריקה) הועברו ל-Backlog ונרשמו כסיכון ב-TEST_PLAN.

**למה:** טסט שמקבע באג יישבר דווקא כשהבאג יתוקן, ויסתיר אותו בזמן שהוא קיים.

| יתרונות | חסרונות |
|---------|---------|
| ריצה מלאה ירוקה, והבאגים עדיין גלויים בדוח | חלק מהבאגים לא נבדקים אוטומטית (נמצאים ב-Backlog) |
| ה-annotation נעלם מעצמו כשהאתר מתוקן, בלי לשנות קוד | צריך קוד שמזהה אם הבאג מופיע (למשל D1 ב-TC-NAV-04) |

### 3.3 Page Object Model עם מחלקות בסיס ורכיבים משותפים

**ההחלטה:**
- `BasePage` מספק `goto()` ו-`waitForLoaded()` מופשט. לכל עמוד יש המתנת מוכנות אחת שבודקת URL ואלמנט מפתח עם `expect` שממתין אוטומטית.
- `AppPage` מוסיף את מה שמשותף לכל עמוד אחרי התחברות: `header`, `menu` (תפריט ההמבורגר) ו-`title`.
- `ItemList` הוא רכיב אחד לשלוש רשימות המוצרים (inventory, עגלה, overview), כי המבנה שלהן זהה.

**למה:** דרישת חובה במשימה, והפרדה בין "איך מוצאים אלמנט" לבין "מה בודקים".

| יתרונות | חסרונות |
|---------|---------|
| שינוי ב-UI מתוקן במקום אחד | עוד שכבת הפשטה שצריך להכיר |
| `ItemList` מונע שכפול לוגיקה בשלושה עמודים | ירושה (BasePage → AppPage → Page) מוסיפה צימוד בין המחלקות |
| `waitForLoaded()` מבטיח שקוראים נתונים רק אחרי שהעמוד באמת התחלף | |

### 3.4 ה-assertions העסקיים נשארים בקבצי ה-spec, לא ב-Page Objects

**ההחלטה:** page object מכיל locators ופעולות בלבד, ואת `waitForLoaded()` כבדיקה היחידה. כל בדיקה עסקית (טקסט, מחיר, מספר פריטים) נכתבת בטסט.

| יתרונות | חסרונות |
|---------|---------|
| אותו page object עובד עם `expect` ועם `expect.soft`, לפי מה שהטסט צריך | קבצי הטסט ארוכים יותר |
| קורא הטסט רואה מיד מה נבדק, בלי לפתוח מחלקות | יש בדיקות שחוזרות בין טסטים (מוקטן בעזרת custom matchers) |

### 3.5 ShopFlow למסעות רב-עמודיים

**ההחלטה:** `ShopFlow` מרכיב את ה-page objects למסעות נפוצים: `addAndOpenCart`, `startCheckout`, `reachOverview`, `placeOrder`. טסט Checkout מגיע לנקודת ההתחלה שלו בשורה אחת.

| יתרונות | חסרונות |
|---------|---------|
| טסטים קצרים וממוקדים במה שהם באמת בודקים | השלבים שבתוך ה-flow פחות גלויים בקוד הטסט |
| שינוי במסלול הקנייה מתוקן במקום אחד | ה-flow חייב להישאר "טיפש" (בלי assertions עסקיים) כדי לא להסתיר כשלים |

### 3.6 נקודת כניסה אחת ל-fixtures עם `mergeTests`

**ההחלטה:** כל spec מייבא רק מ-`@fixtures/index`. שם `test = mergeTests(auth, pages, allure)`, וה-`expect` הוא ה-`expect` המורחב עם ה-custom matchers. ה-page fixtures מזריקים מופע של כל page object (`loginPage`, `inventoryPage`, `cartPage` וכו') ואת `shop`, כולם קשורים ל-`page` של הטסט.

| יתרונות | חסרונות |
|---------|---------|
| ייבוא אחיד בכל הטסטים, אין "איזה test לייבא" | fixture נוסף משפיע על כל הטסטים, ודורש זהירות |
| כל fixture נבדק ומתוחזק בנפרד, והמיזוג מוסיף אותם יחד | page objects נוצרים גם כשטסט לא משתמש בהם (עלות זניחה) |

### 3.7 התחברות פעם אחת לכל worker עם `storageState`

**ההחלטה:** fixture ברמת worker מתחבר דרך טופס ההתחברות האמיתי, פעם אחת לכל צירוף של project (דפדפן), משתמש ו-worker, ושומר `storageState`. כל טסט מקבל browser context חדש מהמצב הזה: הוא מתחיל מחובר, עם עגלה ריקה, ומבודד לחלוטין מטסטים אחרים. `globalSetup` מוחק את קבצי ה-auth בתחילת כל ריצה, כך ש-session לעולם לא עובר בין ריצות.

- **מצב אורח:** `test.use({ storageState: GUEST_STATE })` לטסטים שמתחילים מנותקים (כל טסטי ה-Login ו-TC-NAV-02).
- **משתמש אחר:** `test.use({ authUser: 'problem' })` ברמה העליונה של קובץ ה-spec.

**למה לא setup project?** ה-fixture נוצר בעצלות (lazy) רק כשטסט צריך אותו, ולכן מתנהג אותו דבר בהרצת טסט בודד, בסינון לפי tag או בריצה מלאה, ונוצר מחדש גם אחרי retry (worker חדש).

| יתרונות | חסרונות |
|---------|---------|
| חוסך התחברות בכל טסט, ומקצר משמעותית את הריצה | ההתחברות עצמה לא נבדקת בכל טסט (לכן יש טסטי Login ייעודיים במצב אורח) |
| בידוד מלא: context חדש לכל טסט, אין תלות בין טסטים, ריצה מקבילית בטוחה | `authUser` הוא option ברמת worker, ולכן אפשר לשנות אותו רק ברמת הקובץ |
| התחברות דרך ה-UI האמיתי ולא הזרקת cookie, כך שמצב ה-session אמין | קבצי auth על הדיסק (מוחקים אותם בכל ריצה) |

### 3.8 מדיניות locators: `data-test` בלבד

**ההחלטה:** כל ה-locators משתמשים ב-`getByTestId` עם `testIdAttribute: 'data-test'`. יש בדיוק 4 חריגות, כל אחת מוגדרת פעם אחת ב-page object עם הערה:
- `#react-burger-menu-btn` ו-`#react-burger-cross-btn`: לכפתורים אין `data-test`.
- `.bm-menu-wrap`: התכונה `aria-hidden` שלו היא הסימן האמין היחיד לכך שהתפריט פתוח או סגור.
- `.error_icon`: לאייקוני השגיאה בתוך שדות ההתחברות אין `data-test`.

מזהים עם תווים מיוחדים, כמו `add-to-cart-test.allthethings()-t-shirt-(red)`, מועברים כמחרוזת מדויקת ולעולם לא נבנים לתוך CSS.

| יתרונות | חסרונות |
|---------|---------|
| מזהי `data-test` יציבים, ולא משתנים עם עיצוב או טקסט | לא בודק נגישות כמו locators לפי role (role נוסף רק במקומות שהאפיון דורש) |
| כל החריגות מרוכזות, מתועדות וקלות לאיתור | תלות בכך שהמפתחים ישמרו על המזהים |

### 3.9 נתוני בדיקה מוקלדים ב-`src/data/`

**ההחלטה:** הקטלוג (`PRODUCTS` עם id, slug, שם, מחיר בסנטים ותיאור), סדרי המיון, הודעות ה-UI, הנתיבים, ה-URLs המוגנים, מקרי ההתחברות ועגלות ה-checkout נמצאים בקבצים מוקלדים. אין "magic strings" בטסטים. שמות המשתמשים נבנים בעצלות מתוך `getUser()`, כך שהם תמיד תואמים ל-`.env`.

| יתרונות | חסרונות |
|---------|---------|
| שינוי טקסט באתר מתוקן במקום אחד | הטסט פחות "קריא כטקסט חופשי" (צריך לקפוץ לקובץ הנתונים) |
| טיפוסים כמו `ProductKey` ו-`SortValue` מונעים טעויות כתיב כבר בקומפילציה | הערכים הצפויים נלקחו מצפייה באתר, ויש לעדכן אותם ידנית אם האתר משתנה |

### 3.10 טסטים מקובצים (Grouped verification tests)

**ההחלטה:** לכל אזור יש תקציב של 6 טסטים. בדיקות באותו מבנה (פעולה אחת, הרבה קלטים) אוחדו לטסט אחד מונחה-נתונים עם `runGroupedCases`:
- כל מקרה רץ ב-`test.step` נפרד עם שם (`#3 Unknown user`), עם timeout משלו, ומתחיל באיפוס המצב שלו.
- הבדיקות בתוך מקרה הן `expect.soft`. שגיאה שנזרקת נתפסת ונרשמת למקרה, והמקרה הבא ממשיך לרוץ.
- בסוף מצורף `grouped-summary.md` (מקרה / סטטוס / שגיאה ראשונה) ו-annotation בסגנון `grouped: 13 cases, 13 passed, 0 failed`. אם מקרה כלשהו נכשל, הטסט נכשל עם שגיאה מסכמת אחת.
- ה-runner מגדיל את ה-timeout של הטסט לפי מספר המקרים.

ארבעת הטסטים המקובצים: TC-LOGIN-02 (13 מקרים), TC-LOGIN-04 (4), TC-CHK-03 (10), TC-NAV-02 (12).

**למה לא `for` שיוצר טסט נפרד לכל מקרה?** זה היה חורג מהמגבלה של עד 6 טסטים לאזור.

| יתרונות | חסרונות |
|---------|---------|
| 65 מקרים נבדקים בתוך מגבלה של 30 טסטים | retry מריץ מחדש את כל המקרים של הטסט, לא רק את זה שנכשל |
| כשל במקרה אחד לא עוצר את האחרים, וכל מקרה מופיע כ-step ירוק או אדום בדוח | המקרים רצים בטור בתוך טסט אחד, ולכן הטסט ארוך יותר |
| כל מקרה מתחיל מאיפוס מצב, באותו `page`, כך ש-trace, וידאו וצילום מסך עובדים לכל הטסט | סינון לפי `-g` לא יכול לבחור מקרה בודד |

### 3.11 Custom matchers

**ההחלטה:** שלושה matchers ב-[`matchers.ts`](../src/fixtures/matchers.ts):
- `toHaveCartBadge(header, n)`: ה-badge מציג `n`, ו-`0` אומר שה-badge לא קיים. "לא קיים" נבדק רק אחרי שה-header נטען, כך שעמוד ריק לא יעבור בטעות.
- `toShowProducts(list, keys)`: בדיוק המוצרים האלה, עם שמות ומחירים, בסדר הזה.
- `toHaveOrderSummary(overview, summary)`: שלוש התוויות של סיכום ההזמנה ("Item total", "Tax", "Total").

כולם בנויים מ-web-first assertions, מנסים שוב אוטומטית בתוך תקציב זמן אחד, עובדים עם `expect.soft` ומחזירים הודעת שגיאה קריאה.

| יתרונות | חסרונות |
|---------|---------|
| בדיקה מורכבת בשורה אחת, עם הודעת שגיאה ברורה | `.not` לא נתמך (זורק שגיאה מפורשת) |
| מונע שכפול לולאות בדיקה בין טסטים | קוד נוסף לתחזוקה, ונדרשת הכרה שלו |

### 3.12 חישובי כסף במספרים שלמים (סנטים)

**ההחלטה:** [`money.ts`](../src/utils/money.ts) מבצע את כל חישובי המחיר בסנטים, עם טיפוס ממותג `Cents`: פענוח, עיצוב, ומס של 8% עם עיגול חצי-למעלה. TC-CHK-03 בודק כל עגלה פעמיים, באופן בלתי תלוי: מול הערכים שנצפו באתר, **וגם** מול הכלל.

| יתרונות | חסרונות |
|---------|---------|
| אין סטיות של floating point בחישוב הצפוי | כלל המס (8%, חצי-למעלה) הוסק מהאתר ולא נלקח מאפיון רשמי |
| בדיקה כפולה תופסת גם שינוי בטבלה וגם שינוי בכלל | |
| בזכותו נמצא באג DEF-CHK-SUBTOTAL (סכום לא מעוגל) | |

### 3.13 Soft assertions לצד Hard guards

**ההחלטה:** כשכמה בדיקות בלתי תלויות באות אחרי פעולה אחת, הן `expect.soft`, כדי לראות את כל הכשלים בריצה אחת. כל ניווט שהמשך הטסט תלוי בו מוגן ב-assertion רגיל (hard), בדרך כלל דרך `waitForLoaded()`.

| יתרונות | חסרונות |
|---------|---------|
| ריצה אחת מראה את כל מה שנשבר, לא רק את הכשל הראשון | soft לבד יכול להמשיך לרוץ על עמוד שגוי, ולכן צריך את ה-hard guards |
| ה-hard guard מונע שרשרת כשלים מבלבלת | צריך שיקול דעת מה soft ומה hard |

### 3.14 בלי המתנות קבועות

**ההחלטה:** רק assertions שממתינים אוטומטית (`toHaveURL`, `toHaveText`, `toHaveCount`, `expect.poll`). אין `waitForTimeout`, אין `describe.serial`, ואין מצב משותף בין טסטים. ל-`performance_glitch_user` יש `SLOW_RENDER_TIMEOUT` של 15 שניות.

| יתרונות | חסרונות |
|---------|---------|
| טסטים מהירים ויציבים, שלא תלויים במהירות המכונה | מקרים אסינכרוניים מיוחדים (redirect בצד לקוח, cookies) דורשים `expect.poll` |
| ריצה מקבילית מלאה (`fullyParallel: true`) | |

### 3.15 שלושה דפדפנים

**ההחלטה:** כל טסט רץ על Chromium, Firefox ו-WebKit.

| יתרונות | חסרונות |
|---------|---------|
| תופס בעיות ספציפיות לדפדפן (כך נמצא DEF-NAV-MENU-RACE ב-WebKit) | זמן ריצה פי 3 (כ-2 דקות מקומית) |
| | Mobile viewports לא נבדקים (ראו 3.16) |

### 3.16 מסך מחשב בלבד, לא מסך טלפון

**ההחלטה:** כל הטסטים רצים על מסך מחשב (Desktop viewport) בלבד, דרך פרופילי הדסקטופ של Playwright: `Desktop Chrome`, `Desktop Firefox` ו-`Desktop Safari`. אין projects של טלפון או טאבלט.

**למה:**
- המשימה לא דורשת בדיקות מובייל, ומגבילה כל אזור ל-6 טסטים. העדפנו לנצל את התקציב לעומק הפונקציונלי (התחברות, קטלוג, עגלה, תשלום, הרשאות) ולא לשכפל את אותם תרחישים על גודל מסך נוסף.
- הלוגיקה העסקית באתר זהה בכל גודל מסך: אותם עמודים, אותם מזהי `data-test` ואותו תפריט המבורגר. מסך טלפון היה בודק בעיקר פריסה (layout), וזה קרוב יותר לבדיקות ויזואליות, שגם הן מחוץ להיקף.
- כל project נוסף מכפיל את זמן הריצה. 3 דפדפנים × מחשב כבר נותנים 93 תוצאות בריצה מלאה.

| יתרונות | חסרונות |
|---------|---------|
| מיקוד בבדיקות הפונקציונליות שהמשימה מבקשת | באגים שמופיעים רק במסך קטן (פריסה, אלמנטים מוסתרים או חופפים) לא ייתפסו |
| ריצה מהירה ויציבה יותר | אינטראקציות מגע (tap, swipe) לא נבדקות |
| קל להוסיף בהמשך: ה-page objects מבוססים על `data-test` ולא על מיקום, כך שמספיק להוסיף project עם `devices['Pixel 7']` או `devices['iPhone 15']` ב-`playwright.config.ts` | חלק מהטסטים עשויים לדרוש התאמה במובייל (למשל גלילה או תפריט) |

### 3.17 קונפיגורציה, משתני סביבה וארטיפקטים

**ההחלטות:**
- **`.env` עם fallback ל-`.env.example`:** אם אין `.env`, הקונפיג טוען את `.env.example` ומדפיס הודעה אחת. הקובץ מכיל רק את ערכי הדמו הציבוריים, כך שהפרויקט רץ בשלושה צעדים: clone → install → test. משתנים מה-shell (למשל ב-CI) גוברים על שניהם.
- **`retries: 1`** (דרישת המשימה).
- **ארטיפקטים:** צילום מסך רק בכשל, וידאו ו-trace נשמרים רק בכשל (`retain-on-failure`).
- **Timeouts:** 30 שניות לטסט, 5 שניות ל-expect, 10 שניות לפעולה, 15 שניות לניווט.
- **Workers:** מקומית 4 כברירת מחדל (משתנה `WORKERS` ב-`.env`, מספר או אחוז מליבות ה-CPU), כי יותר מדי דפדפנים במקביל גורמים ל-timeouts ב-Firefox וב-WebKit. ב-CI תמיד 2, כדי שהריצה תהיה צפויה.

| יתרונות | חסרונות |
|---------|---------|
| הפרויקט רץ מיד אחרי clone, בלי שלב הגדרה | ה-fallback עלול להסתיר `.env` חסר (לכן מודפסת הודעה) |
| ב-CI אין צורך ב-secrets | retry יכול להסתיר flakiness (הוא מסומן בדוח כ-flaky) |
| ארטיפקטים רק בכשל חוסכים דיסק וזמן | |

### 3.18 Tags ו-annotations

**ההחלטה:**
- **Tags:** `@smoke` (המסלול הקריטי, `npm run test:smoke`) ו-`@regression` (הסוויטה הרחבה). ארבעה טסטים נושאים את שניהם.
- **`covers`:** כל טסט מציין את ה-ACs שהוא מכסה.
- **`known-issue`:** באג ידוע שהופיע בריצה.
- **`grouped`:** סיכום המקרים של טסט מקובץ.

| יתרונות | חסרונות |
|---------|---------|
| הרצה חלקית לפי מטרה (smoke מהיר, regression מלא) | יש לשמור על התאמה בין ה-tags לטבלה ב-TEST_PLAN |
| עקיבות לאפיון ישירות מתוך הדוח | |

### 3.19 דוחות: Playwright HTML ו-Allure 3

**ההחלטה:** ה-HTML reporter המובנה הוא הדוח הראשי. Allure 3 נוסף כבונוס: ה-CLI שלו הוא חבילת Node, ולכן אין צורך ב-Java. fixture אוטומטי ([`allure.fixture.ts`](../src/fixtures/allure.fixture.ts)) ממפה את ה-annotations ל-labels של Allure: feature לפי אזור, story לפי AC, ו-tag ל-`known-issue`. בריצה מקומית, reporter קטן ([`allure-open.reporter.ts`](../src/reporters/allure-open.reporter.ts)) מייצר את דוח Allure ופותח אותו בדפדפן.

| יתרונות | חסרונות |
|---------|---------|

| הדוח נפתח לבד בסוף ריצה מקומית (ניתן לכבות עם `ALLURE_OPEN=false`) | שרת דוח שנשאר לרוץ ברקע (מוסבר ב-README איך לעצור אותו) |

### 3.20 CI ב-GitHub Actions

**ההחלטה:** ג'וב typecheck, ג'וב נפרד לכל דפדפן עם `fail-fast: false`, ג'וב שמאחד את ה-blob reports ל-HTML report אחד ואת תוצאות Allure לדוח אחד, ופרסום ל-GitHub Pages רק ב-push ל-`main`.
